Porting the ARM toolchain (o5a/o5l) against goken, byte-equal
===============================================================

Goal: automate porting the rest of the ARM linker/assembler (o5a/o5l)
from the goken reference (~/goken, a C Plan 9 toolchain fork), driven
by differential testing: assemble+link the same .s with both goken's
5a/5l and xix's o5a/o5l, and require the final executables to be
byte-identical. Scope is ARM assembler + linker only, permanently --
not phase-1-of-N. The compiler is explicitly NOT part of this
byte-equal effort (see "Compiler is out of scope" below); there is no
planned phase 2 that extends this harness to o5c vs goken's 5c.

This is the forward-looking counterpart, for the OCaml port, of what
goken's own docs/claude_notes/notes_arch_arm.txt did for reconciling
two *C* lineages (5a/5c/5l vs 5ak/5ck/5lk) byte-for-byte. Same kind of
problem, same kind of playbook, different target language.

Grounding: how goken maps onto xix
-----------------------------------

goken's linkers/5l/ was itself split into codegen.c, datagen.c,
layout.c, profile.c, debugging.c, dynamic.c, hist.c, io.c, lib.c,
main.c, etc. This split is exactly what xix's linker/ module layout
mirrors (Codegen5.ml, Datagen.ml, Layout5.ml, Profile.ml, ...), which
confirms goken/linkers/5l/codegen.c is the right C reference for the
`(* case N: ... *)` comments already present in Codegen5.ml -- it has
the numbered asmout-style switch (~70 cases), e.g.:

    case 34: /* mov $lacon,R -> LDR x(R15), R11; ADD R11, R13, R */

goken's own reference binaries are already built at
~/goken/ROOT/arch/boot-gcc/bin/{5a,5l} (invoke directly, no rebuild
needed unless goken's C source itself changes).

xix/linker/TOPORT/5l/ and xix/assembler/TOPORT/5a/ hold an *older*
snapshot of the same C sources (predates goken's file-split reorg --
e.g. TOPORT/5l/asm.c is still the pre-split monolith). goken is the
more up-to-date and better-organized reference to port from and to
diff against; treat TOPORT/ as historical/secondary.

Current state of Codegen5.ml
------------------------------

Only these goken codegen.c cases currently have matching
`(* case N: *)` comments in Codegen5.ml: 1, 2, 3, 5, 6, 7, 8, 9, 10,
15, 41.

Several spots are stubbed `(* case ?? *)` with the real case number
never pinned down (lines ~429, 446, 453, 532, 551, 599, 625 as of this
writing) -- resolving these against codegen.c is itself backlog work,
separate from porting brand-new cases.

Everything else in codegen.c's switch is unported: arithmetic/const
variants (4, 12, 13, 14, 16, 17, 58), load/store variants (20-23,
30-34, 59-63, 70-73), branch/switch (62, 63 "bcase"), PSR/movm/swi/
swap (35-40, 64-67), floating/VFP (50-57, 68, 69, 74-76).

Three important facts that shape the harness
-------------------------------------------------

1. Object file format is intentionally NOT shared between goken and
   xix. assembler/objects/Object_file.ml uses OCaml Marshal (`.o5`/
   `.ov` extension, magic 8495a6be) instead of replicating Plan 9's
   on-disk object format -- this is a deliberate simplification
   documented in assembler/CLI.ml's prelude ("use of simple
   marshalling instead of adhoc object format"). Consequence: never
   try to diff or interop .5 vs .o5 files. Only final linked
   executables are ever compared.

2. goken's 5l defaults to the Plan 9 native "a.out" header (HEADTYPE
   H_PLAN9=2, see linkers/5l/l.h). ELF is H_ELF=7, selected with
   `5l -H7`. xix's o5l always emits ELF. So the harness must pass
   `-H7` on the goken side, or the outputs aren't even the same
   container format.

3. This machine is arm64 and has qemu-arm installed, so 32-bit ARM
   Linux ELF binaries can actually be *run*, not just byte-compared.
   That's a stronger, cheaper first signal than `cmp` and should be a
   first-class step of the harness, not an afterthought: assemble,
   link, `chmod +x`, then `qemu-arm ./t.out` and check its stdout and
   exit code.

Given (3), the right starting fixture is a *Linux* hello world (real
`write`/`exit` syscalls, SWI $0, syscall number in R7 -- the standard
Linux ARM EABI convention) rather than tests/linker/helloworld.s
(which uses Plan 9's native EXITS/PWRITE syscall numbers and only
makes sense with `-H2`/native Plan 9 headers, not something qemu-arm
on Linux can run). tests/assembler/hello_linux_arm.s already is that
program; it's now also copied to
tests/linker/arm_diff/hello_linux_arm.s (see "Test corpus sources"
below for why it's its own subfolder there) as the designated
starting-point fixture for the harness. It needs one adjustment
either toolchain-side: it defines TEXT `_start`,
not the linkers' default entry symbol `_main`, so both sides need an
explicit entry flag:
  goken: 5a -o t.5 t.s  &&  5l -H7 -E _start -o t.out t.5
  xix:   o5a -o t.o5 t.s  &&  o5l -E _start -o t.out t.o5
(o5l already defaults its header type to elf, and its `-E` flag
mirrors goken's; note OCaml's Arg wants `-E _start` as two argv
words, not glued as `-E_start` the way goken's getopt-style parsing
tolerates.)

Verified by hand with exactly this recipe:
  - goken's build actually **runs** under qemu-arm: prints
    "Hello, world" and exits 0.
  - xix's build **crashes**: `qemu-arm ./t.out` reports "uncaught
    target signal 4 (Illegal instruction)". This is a real,
    functional correctness bug, found before even getting to
    byte-diffing -- exactly the kind of signal phase 0 should surface
    early and often.
  - `cmp -l` on the two ELF files: sizes differ by 176 bytes (4288
    goken vs 4112 xix), and the first differing byte is offset 33 --
    i.e. still inside the ELF header/program-header area, not in the
    code. That's consistent with the "no section header" vs
    "stripped" discrepancy noted above: this looks like an ELF
    container/segment-layout difference more than a codegen
    difference, and is likely *why* qemu then executes garbage and
    hits an illegal instruction. This needs to be run down (ELF
    layout parity) before per-case codegen porting can produce
    meaningful, attributable diffs.

Separately: o5l currently exits 0 even when it hits a real
`error node "TODO: ..."` (as opposed to a merely harmless log like the
`Codegen5.LPOOL` no-op in Layout5.ml, which fires on every
unconditional branch as a placeholder for goken's `checkpool()` --
see layout.c's checkpool/flushpool/addpool trio -- but doesn't by
itself corrupt output since it only ever needs to do an *early* pool
flush on inputs way larger than anything in this initial corpus). The
o5l exit-code gap is a harness-breaking bug: a broken/unimplemented
case must not look like a silent pass.

Phase 0 -- build the differential harness (one-time)
--------------------------------------------------------

1. Fixture/runner: a plain bash script (scripts/diff-arm.sh, driven
   over the baseline corpus by test-arm.sh at the repo root, mirroring
   test.sh's style), NOT a Testo module/test. Testo is reserved for
   this project's actual correctness test suite (`make test`), which
   must run without any external toolchain installed; this harness
   has a hard dependency on a locally built goken checkout and is a
   development/porting tool, not a CI test. Per test file (see exact
   flags under "Verified by hand" below -- entry point is `_start`,
   not the linkers' default `_main`):
     goken: 5a -o t.5 t.s && 5l -H7 -E _start -o t.out.goken t.5
     xix:   o5a -o t.o5 t.s && o5l -E _start -o t.out.xix t.o5
     cmp -l t.out.goken t.out.xix   (report byte offsets, not just
                                     pass/fail -- needed to debug which
                                     case regressed)
     qemu-arm ./t.out.{goken,xix}   (functional smoke test -- see
                                     "Three important facts" above;
                                     run this even when `cmp` already
                                     disagrees, since it can point
                                     more directly at "structural"
                                     vs. "wrong instruction" bugs)
   goken's location comes from an env var (GOKEN_ROOT, default
   ~/goken); tests skip (not fail) when it's unset/missing so `make
   test` stays green without goken installed.

2. Fix exit-code propagation in o5l's error path so an unimplemented
   case (`error node "TODO: ..."`) causes a non-zero exit -- otherwise
   the harness can't trust "link succeeded" as a signal at all. This
   fix belongs in xix (see "Where changes land" below).

3. Confirm ELF layout parity: check Layout5.ml's INITTEXT/INITDATA/
   INITRND for ARM+ELF against goken's l.h/main.c equivalents. Also
   `file` reports o5l's ELF as "no section header" vs goken -H7's
   output as "stripped" -- these need to agree structurally before any
   codegen case can byte-match, independent of codegen correctness.

4. First concrete run: tests/linker/arm_diff/hello_linux_arm.s (copied from
   tests/assembler/, same content). Small, self-contained (TEXT
   _start + write + exit, one data GLOBL), and -- crucially -- an
   actual runnable Linux ELF binary rather than a Plan-9-native one,
   so both `cmp` and qemu-arm apply to it. Get the harness itself
   working end to end on this one file before worrying about breadth.

Test corpus sources
----------------------

The diff fixtures live under tests/linker/arm_diff/: each one is a
single object file (one TEXT, assembled and laid out directly), so
what's actually being exercised is mostly assembler codegen + minimal
exec-layout, not linking proper (no cross-object symbol resolution,
no archives) -- still filed under tests/linker/ since it's o5a+o5l's
combined output being differential-tested, with a sibling
tests/linker/mips_diff/ expected once MIPS (ovl vs goken's vl) gets
the same treatment.

Beyond tests/linker/'s other fixtures (hello.s, world.s, helloworld.s
-- Plan 9-native, kept where they are, unrelated to this differential
effort),
goken ships its own ARM assembly fixtures at ~/goken/tests/s/mini/
(and tests/s/{exit,features,float,hello_arch,regressions,variants}/
for the wider arch set) -- reuse those instead of inventing everything
from scratch when extending tests/linker/arm_diff/'s phase-0.5 baseline
corpus and the per-case fixtures in phase 1. They're already
known-good inputs to the C reference, and goken's tests/s/variants/
in particular are curated regression tests for specific past bugs
(e.g. addr_arm.s for the $sym(SB) operand path, call_arm.s for BL),
which makes them good fixtures on our side too. Prefer ones that use
real Linux syscalls with a Linux-friendly entry point, so qemu-arm can
double-check them too; the Plan-9-native ones (hello.s/world.s/
helloworld.s style, EXITS/PWRITE syscalls) are still useful for
`cmp`-only comparison against goken's `-H2` default but can't be run
under qemu-arm on this Linux host.

Also: `cmp`-clean isn't a strong enough check on its own for a fixture
with no data section. tests/linker/arm_diff/exit_linux_arm.s (no GLOBL/DATA
at all) caught a 1-byte size bug in Elf.ml's shstrtab content (missing
one of goken's two trailing NULs, see elfstrtab() in 8l/elf.c) that
tests/linker/arm_diff/hello_linux_arm.s could not have caught: that fixture's
section-header/string-table region sits in the zero-padded gap before
its data segment, so a byte too few there just disappears into
already-zero padding instead of changing the file's total size.
Keep at least one no-data-section fixture in the corpus for that
reason.

Syncweb: hard constraint, both repos
----------------------------------------

Both xix and goken source files are synced to Noweb literate-
programming docs via `(*s: ... *)` / `(*e: ... *)` / `(*x: ... *)`
comments (`/*s: ... */` etc. in goken's C). Never add, remove, or
modify these markers in either codebase during this work, in either
direction. Concretely:
  - Editing the *body* of an existing chunk (the code between an
    existing s:/e: pair) is fine -- that's how tracked code normally
    evolves.
  - Do NOT introduce brand-new `(*s: ...*)`/`(*e: ...*)` wrappers for
    new functions/types added while porting; write new code as plain
    OCaml (or plain C on the goken side) without inventing chunk
    names, and leave wiring it into the literate docs to the project
    owner.
  - Never rename, move, or delete an existing marker line, even when
    refactoring the code it wraps.

Where changes land: xix vs goken
-------------------------------------

The bulk of this effort is xix-side porting/fixes (Codegen5.ml,
Layout5.ml, the harness itself, exit-code handling, etc.) -- goken is
the reference and should stay stable by default.

It is fine, though, to make small, reasonable, flag-gated adjustments
to goken itself when they help reach a byte-matching baseline faster
-- e.g. a flag to disable an optimization pass, suppress extra debug
info, or otherwise simplify its output so the comparison isolates the
construct actually being ported rather than an unrelated goken-side
knob. Keep such changes minimal, opt-in (a new flag, not a changed
default), and still fully respecting goken's own syncweb markers under
the same rule as above. When in doubt, prefer solving it on the xix
side instead.

Phase 0.5 -- baseline: prove byte-equality on what already works
----------------------------------------------------------------------

Before touching any unimplemented case, build a small corpus of .s
fixtures that only exercise the constructs already ported (cases 1,
2, 3, 5, 6, 7, 8, 9, 10, 15, 41 -- op R,[R],R / movbu $I,[R],R / add
R<<[IR],[R],R / sll / mul / branches / swi / rfe) and run the phase-0
harness on all of them. Fix whatever it takes (layout/header parity,
symbol/relocation ordering, padding) to get these to `cmp` clean
first. Only once this baseline is solid does a byte mismatch on a
*new* case reliably mean "this case's codegen is wrong" rather than
"something structural is still off" -- so this step is what makes the
rest of the loop trustworthy, not optional scaffolding.

Phase 1 -- the porting backlog and per-case workflow
---------------------------------------------------------

Backlog = every numbered case in goken's codegen.c switch not yet in
Codegen5.ml (see list above). Tracked as a checklist in
docs/claude_notes/todo_arm_port.org (xix/todo.org itself is large and
covers the whole project, so this plan gets its own progress file
instead) -- check case items off there as they're ported, rather than
here.

Per case N:
  1. Read codegen.c's `case N:` block and its comment.
  2. Add the matching OCaml arm in Codegen5.ml, tagging *both* the
     outer dispatch and any inner sub-match with
     `(* case N: <verbatim C comment> *)`, exactly like the existing
     1/2/3 and 8/9 cases (two placements: where the instruction shape
     is recognized, and where the specific operand sub-case is
     generated). Note there's no optab/oplook table in the OCaml port
     ("ocaml: No need for optab/oplook/ocmp/cmp as in 5l. Just use
     pattern matching!") -- porting a case means adding a pattern-match
     arm, not filling a table row.
  3. Write a minimal .s fixture isolating just that construct, under
     tests/linker/arm_diff/.
  4. Run the phase-0 harness on that fixture; iterate on the `cmp -l`
     offsets until byte-identical.
  5. Commit case-by-case (small, reviewable diffs), not batched.

hello_linux_arm.s is the designated first data point (see Phase 0,
item 4) rather than a specific "first case": run the harness on it,
read the `cmp -l` output and the qemu-arm result, and let that
determine what the first real fix is. The evidence gathered so far
(176-byte size gap, first mismatch at ELF-header offset 33, xix's
binary SIGILL-ing under qemu-arm) points at ELF container/segment
layout (Phase 0 item 3) as the most likely first thing to fix, ahead
of any specific codegen case. Resist fixing anything ARM-codegen-
related before the harness has actually produced a byte-level diff to
point at.

Compiler is out of scope
----------------------------

occ (xix's C compiler) is *not* going to be ported/kept byte-equal
against goken's per-arch compilers (5c/6c/7c/8c/vc/ic/...). goken
duplicates a lot of codegen logic across those per-arch compilers;
the actual plan for occ is to instead reuse ~/c--'s backend
architecture (a fork of Quick C--, at ~/github/fork-c--, with a
proper shared arch/backend/ split instead of one-file-per-arch
duplication). So this differential-testing/byte-equal methodology
stays scoped to the assembler+linker (o5a/o5l vs goken's 5a/5l); it
is not meant to be extended to the compiler later, and o5c vs 5c
byte-equality is explicitly not a goal.
