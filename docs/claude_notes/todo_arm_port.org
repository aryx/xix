** MAJOR FIND, FIXED: immrot() was subtly wrong for some values --
   goken's own `immrot(ulong v)` (5l/span.c) is, relative to true ARM
   rotated-immediate semantics, buggy on a 64-bit host: `ulong` is
   64-bit unsigned here (typedef in include/core/types.h), but the
   rotation trick (`v = (v<<2)|(v>>30)` up to 16 times) was written
   assuming 32-bit wraparound. On a 64-bit `ulong`, bits pushed past
   bit 63 are simply lost and `v>>30` starts pulling in bits that
   never actually wrapped around from a genuine 32-bit rotation --
   so for some values that ARE valid ARM rotated immediates (e.g.
   0x9000 = 0x90 rotated), goken's own immrot() returns 0 (not
   encodable), and it takes the literal-pool slow path (case 12/34)
   instead of a single MOV/ADD (case 2/4). Since the whole point of
   this port is byte-for-byte matching THIS actual goken binary (not
   "more correct" ARM codegen), Codegen5.ml's immrot needed to
   replicate that exact 64-bit non-wrapping computation, not the
   mathematically-correct 32-bit version it had before -- rewritten
   using Int64 (OCaml's native int can't safely hold the needed
   64-bit unsigned patterns). This was previously undetected because
   every earlier fixture's constants either fit directly (0-255, way
   below where the two versions could ever disagree) or were clearly
   too large either way (like 0x12345678); tests/linker/arm_diff/
   swp_arm.s's `MOVW $0x9000, R4` is what exposed it. Re-verified
   the entire existing corpus (all fixtures using case 2/4/12/13/34)
   still passes byte-identical after the fix -- nothing had
   coincidentally depended on the old, wrong 32-bit behavior.
