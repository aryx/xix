Porting the RISC-V (RV32) toolchain (oia/oil) against goken, byte-equal
=========================================================================

Goal: same as docs/claude_notes/notes_arm_port_plan.txt and
notes_mips_port_plan.txt, mirrored for RISC-V: assemble+link the same
.s with both goken's ia/il (Plan 9 RISC-V assembler/linker) and xix's
oia/oil, and require the final executables to be byte-identical.
Scope is RISC-V (RV32, thechar 'i') assembler + linker only, same
reasoning as the other two docs for why the compiler stays out of it.

Read notes_arm_port_plan.txt first -- this doc only calls out what's
RISC-V-specific or different; the general approach (harness shape,
syncweb rules, where changes land, goken flag adjustments allowed) is
identical and not repeated here.

Bigger step than ARM/MIPS: starting from nothing
------------------------------------------------------

Unlike ARM/MIPS, where only bugs needed fixing in an existing port,
RISC-V's *linker* didn't exist in xix at all before this (only the
assembler, oia, had been started) -- CLI.ml's `link` and
`config_of_header_type_and_flags` both had `| _ -> failwith "arch not
supported yet"` for anything but Arm/Mips. New from scratch, mirroring
the ARM/MIPS module split exactly:
  - Typesi.ml (mirrors Typesv.ml)
  - Layouti.ml/.mli (mirrors Layoutv.ml -- simpler, see below)
  - Rewritei.ml (mirrors Rewritev.ml -- the leaf/frame logic is
    genuinely more nuanced than MIPS's, see below)
  - Codegeni.ml/.mli (mirrors Codegenv.ml, case-N tagged against
    goken's il/asm.c)
  - CLI.ml: added `linki` (mirrors link5/linkv), wired into `link`'s
    dispatch, "oil" into the argv0 arch-detection, and RISC-V's
    INITTEXT default (0x10000) into config_of_header_type_and_flags.
  - linker/dune: added `(Main.exe as oil)` to the install stanza
    (mirrors how o5l/ovl already share the one Main.exe, dispatching
    on argv0 at runtime -- no new dune executable needed).
  - assembler/objects/Object_file.ml: `is_obj_filename`'s regex was
    `.*\.o[5v]$` (ARM/MIPS only) -- added 'i' for RISC-V's .oi.
  - linker/executables/Elf.ml: `int_of_machine`'s MRiscv case was
    `failwith "TODO"` -- filled in with 243 (EM_RISCV, the standard
    ELF machine ID).

A real, blocking bug found in the *assembler* first
---------------------------------------------------------

Before any of the linker work could even be tested, hello_linux.s
wouldn't assemble at all with oia: "Syntax error, last name: MOVW".
Root cause, in assembler/Parse_asmi.ml: the entire keyword-recognition
table (the `match s with "MOVW" -> ... | "ECALL" -> ... | ...` block
translating identifier tokens into instruction tokens) was a
copy-pasted-then-commented-out ARM template (Parse_asm5.ml's table,
complete with ARM-only mnemonics like SWI/RFE/BHI/CMPF that don't
exist on RISC-V), never adapted to Ast_asmi's actual grammar. Two
concrete mismatches: it tried to produce a `TMOV` token, which
Parser_asmi.mly doesn't even declare (it uses TMOVE1/TMOVE2, matching
Ast_asmi's more refined Move1/Move2 split, not ARM's single TMOV/
MOVE); and it used TSWI instead of the real TSYSCALL token.
Fixed by wiring up exactly what's currently exercised: "MOVW" ->
TMOVE2 W__ (word-sized general move, immediate/entity/register --
matches ARM/MIPS's unified Move2 usage) and "ECALL" -> TSYSCALL. Left
everything else (MOVB/MOVH/MOVBU/MOVHU, arithmetic, branches, JAL/
JALR as user-written mnemonics) as real backlog -- not guessed at,
since Move1 vs Move2's exact intended split for byte/half moves isn't
obvious from the AST alone (see the "Not yet wired in the assembler"
note below).

A second real discovery: goken's il compresses instructions (RVC)
--------------------------------------------------------------------------

goken's il applies RISC-V's "C" (compressed instruction) extension by
default -- 16-bit encodings for eligible instructions -- via
linkers/il/compress.c, called unconditionally from asm.c's main
encode loop unless `-c` is passed (`if(!debug['c'] && o->ctype) ...`,
mirroring the existing `-s` strip-symbol-table precedent exactly:
a debug-flag-gated behavior, not something hardcoded on). Confirmed
by disassembling goken's default output for hello_linux.s: it
starts with the same lui/addi pair oil produces, then hits 16-bit
opcodes capstone (configured for plain RV32) can't decode -- e.g.
bytes 05 45 decode as `C.LI a2, 13` in the RVC encoding, replacing
what would otherwise be a 4-byte `addi a2,zero,13`.

Decision: this port never emits compressed instructions (a real,
substantial feature -- deciding when a 32-bit instruction can be
losslessly shrunk to 16 bits, which cascades into re-doing layout
since it changes instruction sizes/addresses -- disproportionate to
implement right now). The harness always passes goken's own `-c` to
disable compression on its side, so the comparison is apples to
apples. qemu-riscv32 handles the resulting plain-32-bit-instruction
binaries fine either way (compression support in the emulator isn't
what's in question here -- the compiled bytes themselves just never
use it).

The address-of-global (RSB/BIG) story: closer to ARM than MIPS
--------------------------------------------------------------------

RSB (aka SB, aka gp/x3 in the real ISA) is set up at program start
via `MOVW $setSB(SB), RSB`, the RISC-V analogue of ARM's R12/setR12
and MIPS's R30/setR30. goken's il/span.c aclass() (the D_ADDR/SDATA
case) has the same shape as the other two archs:
    instoffset = s->value + a->offset - BIG
    if(instoffset >= -BIG && instoffset < BIG && instoffset != 0)
        -> fast path: ADDI rd, RSB, instoffset
    else
        -> slow path: absolute address via LUI+ADDI
BIG = 2048 (linkers/il/l.h) -- unlike MIPS's dead BIG=0, this is a
*live* value, and not a coincidence: 2048 is exactly the magnitude of
a signed 12-bit immediate's range, so "does instoffset fit BIG" and
"does instoffset fit ADDI's immediate field" are the same check. That
makes RISC-V's encodability test a plain range check (`fits_addi_imm`
in Codegeni.ml) rather than ARM's bit-rotation search (immrot) --
genuinely simpler than ARM here, while still being a *live* fast path
(unlike MIPS).

Built this correctly from the start rather than discovering it later
via a kitchen-sink fixture (as happened for both ARM and MIPS):
hello_linux.s itself already exercises both paths --
`MOVW $msg(SB), R11` takes the fast path (msg's offset is small), and
`MOVW $setSB(SB), RSB` takes the slow path (the explicit `!= 0`
exclusion is what forces it there, unlike ARM where the exclusion
happened to not matter because immrot(-BIG) also independently
failed -- see notes_arm_port_plan.txt's own writeup of that). Also
note: setSB's own xdefine'd value is BIG (matching goken's
`xdefine("setSB", SDATA, 0L+BIG)` exactly), unlike xix's own ARM
convention which uses 0 for setR12 (works there only because immrot
happens to also reject that case -- a coincidence, not a faithful
mirror of the C). Built RISC-V's the faithful way since there was no
existing convention to inherit.

RISC-V has no branch-delay slots (a real MIPS-specific complication that doesn't apply here)
---------------------------------------------------------------------------------------------------

Unlike MIPS (see notes_mips_port_plan.txt's whole branch-delay-slot
saga), RISC-V jumps/branches take effect immediately -- no slot to
fill, no NOP, no goken sched.c-style hoisting to worry about
replicating. Rewritei.ml's RET/JMP expansion is correspondingly
simpler than Rewritev.ml's.

The leaf/frame logic (RET expansion) is genuinely 3-way, not 2-way like MIPS
------------------------------------------------------------------------------------

Ported from goken's il/noop.c (the ATEXT and ARET cases), which
distinguishes three cases, not two:
  1. leaf, no locals (declared size 0): no prologue/epilogue at all,
     RET is just `JMP (RLINK)`.
  2. leaf, with locals (has a nonzero declared frame but makes no
     calls, so RLINK is never clobbered): prologue only adjusts SP
     (no RLINK save); RET's epilogue adjusts SP back and jumps, no
     restore either.
  3. not leaf (makes a call, clobbering RLINK): full save-adjust-SP
     prologue and restore-adjust-SP-jump epilogue.
Rewritev.ml (MIPS) only distinguishes case 1 from "everything else"
(always doing the full save/restore even for a leaf procedure that
merely has locals) -- whether that's actually a latent MIPS
correctness gap (goken's vl/noop.c wasn't rechecked for this when
writing this doc) or a deliberate simplification isn't determined;
not fixed there since no MIPS fixture exercises it. Built correctly
for RISC-V from the start since the C source was already open.

Not yet wired in the assembler (Parse_asmi.ml)
---------------------------------------------------

MOVB/MOVH/MOVBU/MOVHU (sign/zero-extending byte/half moves, likely
via Ast_asmi's Move1 rather than Move2 -- the asymmetry between
Move1's B_/H_ variants (take just a `sign`) and its W_/V_ variants
(take a `move_dir`) suggests Move1 might be LOAD-only, with byte/half
*stores* going through some other path not yet identified), and any
arithmetic/branch/JAL mnemonics as user-written source (TARITH/TB/
TJAL tokens exist in the grammar and Codegeni.ml has no encoder for
most of them yet either). Deferred rather than guessed at; revisit
once a fixture actually needs one.

Test corpus
--------------

tests/linker/riscv_diff/, sibling to arm_diff/ and mips_diff/. First
fixture: hello_linux.s, copied from goken's tests/s/mini/ (same
"start with the simpler upstream version, not xix's own more elaborate
tests/assembler/ copy" reasoning as the other two archs). PASS:
byte-identical + matching qemu-riscv32 behavior on the very first
successful link, once the assembler bug, the -c flag, and the BIG/
fits_addi_imm formula were all in place.

Harness: scripts/diff-riscv.sh + test-riscv.sh, structurally
identical to the ARM/MIPS ones. Entry point is `_start` (not the
linkers' default `_main`), same as every other arch's fixtures so
far -- pass `-E _start` on both sides. No `-H` flag needed (oil's
CLI.ml already defaults header_type to "elf" regardless of arch, same
as every other arch); goken's il needs `-c -s` (see above) but no
explicit `-H` either (RISC-V's C reference story for that hasn't been
checked, but the default already produced a RISC-V ELF in testing).
